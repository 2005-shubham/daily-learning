# JWT

## What is it?

JSON Web Token (JWT), pronounced "jot," is an open standard (RFC 7519) that defines a compact and self-contained way for securely transmitting information between parties as a JSON object. This information can be verified and trusted because it is digitally signed.

Think of a JWT as a special kind of digitally signed ID card or passport for your application. When a user logs in, instead of giving them a traditional "session ticket" that the server needs to keep track of, the server gives them this "digital passport." This passport contains verifiable claims about the user (e.g., their ID, username, admin status) and is signed by the server's secret key. Every time the user makes a request, they present this passport. The server can then quickly verify the signature to ensure the passport hasn't been tampered with and trust the claims inside, all without needing to consult a database for session information.

A JWT typically consists of three parts, separated by dots (`.`):

1.  **Header:** Contains metadata about the token itself, specifically the type of token (JWT) and the signing algorithm used (e.g., HMAC SHA256 or RSA).
2.  **Payload:** Contains the "claims" – statements about an entity (typically the user) and additional data. Claims can be registered (standardized, e.g., `iss` for issuer, `exp` for expiration), public (custom but collision-resistant), or private (custom, used between specific parties). This is where you put user-specific data like `userId`, `role`, etc.
3.  **Signature:** Created by taking the encoded Header, the encoded Payload, a secret key, and the algorithm specified in the header, and then signing it. This signature is used to verify that the sender of the JWT is who it says it is and that the message hasn't been changed along the way.

The entire token is then Base64Url-encoded, making it compact and URL-safe, suitable for transmission within URL parameters, POST body, or HTTP headers.

## Why is it important?

JWTs have become a cornerstone of modern web and mobile application development due to several key advantages, primarily centered around authentication and authorization in distributed systems.

1.  **Stateless Authentication:** In traditional session-based authentication, the server maintains session state (e.g., in memory or a database). With JWTs, after a user logs in and receives a token, the server no longer needs to store session information. Each subsequent request includes the JWT, allowing the server to verify the user's identity and permissions purely by validating the token's signature. This is crucial for building scalable, stateless APIs and microservices.
2.  **Scalability:** Since servers don't need to maintain session state, you can easily scale your application horizontally by adding more servers. Any server can process a request with a valid JWT without needing to share session data with other servers.
3.  **Cross-Origin & Cross-Device Compatibility:** JWTs are independent of any specific domain or platform. A token issued by an authentication service can be used by various backend services (APIs) and client applications (web, mobile, desktop), regardless of their origin.
4.  **Authorization:** JWTs can carry authorization information directly within their payload (e.g., user roles, permissions). This allows API endpoints to quickly determine if a user has access to a resource without making additional database queries.
5.  **Information Exchange:** JWTs can be used to securely transmit any information between parties. As long as both parties trust the issuer and the secret, the integrity of the data is guaranteed by the signature. This is useful for things like single sign-on (SSO) systems where a user authenticates once with an identity provider and receives a token that grants access to multiple service providers.

## Real World Example

Consider a typical web application with a frontend (e.g., React, Angular, Vue) and a backend API (e.g., Node.js, Python Flask, Java Spring Boot).

1.  **User Login:** A user opens the frontend application and enters their username and password on a login page.
2.  **Authentication Request:** The frontend sends these credentials to the backend API's `/login` endpoint.
3.  **Token Issuance:** The backend receives the credentials, validates them against its user database. If valid, it generates a JWT containing claims like `userId`, `username`, and `role`. It signs this token with a secret key and sends it back to the frontend.
4.  **Token Storage:** The frontend receives the JWT and typically stores it in a secure place, like an `HttpOnly` cookie or in memory (with proper safeguards).
5.  **Protected Resource Access:** The user then navigates to a protected part of the application (e.g., their profile page, an admin dashboard). The frontend attaches the stored JWT to the `Authorization` header of every subsequent HTTP request to the backend, usually as a Bearer token: `Authorization: Bearer <your-jwt-token>`.
6.  **Token Verification:** When the backend receives a request with a JWT, it first extracts the token. Then, it uses the same secret key to verify the token's signature and checks its expiration. If the signature is valid and the token is not expired, the backend trusts the claims within the payload (e.g., `userId`, `role`) and grants access to the requested resource or performs the requested action.
7.  **Logout:** When the user logs out, the frontend simply discards the JWT. On the backend, if token revocation is implemented (e.g., blacklisting), the token might be added to a list of invalidated tokens.

This flow enables stateless, scalable authentication for the application, allowing the backend to focus on business logic rather than session management.

## Syntax / Example

A JWT typically looks like this:

`eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c`

This is composed of three parts:

*   **Header (Base64Url encoded):** `eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9`
    *   Decoded: `{"alg":"HS256","typ":"JWT"}`
*   **Payload (Base64Url encoded):** `eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ`
    *   Decoded: `{"sub":"1234567890","name":"John Doe","iat":1516239022}`
*   **Signature:** `SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c`

### Node.js Example (using `jsonwebtoken` library)

First, install the library:
`npm install jsonwebtoken`

Then, use it in your code:

```javascript
const jwt = require('jsonwebtoken');

// A strong, unique secret key (KEEP THIS SECURE AND OUT OF VERSION CONTROL!)
const JWT_SECRET = 'your_super_secret_key_that_no_one_should_ever_guess_or_know';

// 1. Creating (Signing) a JWT
function generateToken(user) {
    const payload = {
        userId: user.id,
        username: user.username,
        role: user.role
    };

    // Options for the token: expiration, issuer, etc.
    const options = {
        expiresIn: '1h', // Token expires in 1 hour
        issuer: 'your-app-name'
    };

    try {
        const token = jwt.sign(payload, JWT_SECRET, options);
        console.log('Generated JWT:', token);
        return token;
    } catch (error) {
        console.error('Error generating token:', error.message);
        return null;
    }
}

// 2. Verifying a JWT
function verifyToken(token) {
    try {
        const decoded = jwt.verify(token, JWT_SECRET);
        console.log('Decoded Payload:', decoded);
        return decoded; // Contains userId, username, role, iat, exp, iss
    } catch (error) {
        console.error('Error verifying token:', error.message);
        // Common errors: TokenExpiredError, JsonWebTokenError (e.g., invalid signature)
        return null;
    }
}

// --- Usage Example ---
const user = {
    id: 'user123',
    username: 'testuser',
    role: 'admin'
};

const myToken = generateToken(user);

if (myToken) {
    // Simulate some delay for verification
    setTimeout(() => {
        console.log('\nVerifying the token...');
        const verifiedPayload = verifyToken(myToken);
        if (verifiedPayload) {
            console.log('Token is valid for user:', verifiedPayload.username);
        } else {
            console.log('Token is invalid or expired.');
        }

        // Example of an invalid token (tampered with)
        const tamperedToken = myToken.slice(0, -5) + 'xxxxx'; // Change last few chars
        console.log('\nVerifying a tampered token...');
        verifyToken(tamperedToken); // This will fail due to invalid signature

    }, 100);
}

// Example of an expired token (for demonstration, set expiresIn very short)
// const expiredTokenOptions = { expiresIn: '1s', issuer: 'your-app-name' };
// const expiredToken = jwt.sign(user, JWT_SECRET, expiredTokenOptions);
// setTimeout(() => {

//     verifyToken(expiredToken); // This will eventually fail with TokenExpiredError
// }, 2000); // Wait 2 seconds for it to expire
```

## Advantages

*   **Statelessness & Scalability:** Eliminates the need for server-side session storage, allowing for highly scalable and distributed applications without sticky sessions.
*   **Decentralized:** Can be issued by one service and consumed by multiple other services, making it ideal for microservices architectures and Single Sign-On (SSO).
*   **Portability & Cross-Platform:** Being self-contained and URL-safe, JWTs can be easily used across different domains, clients (web, mobile, desktop), and programming languages.
*   **Security (Data Integrity):** The digital signature guarantees that the token's content has not been tampered with since it was issued, ensuring data integrity.
*   **Performance:** Verification is often faster than database lookups required for traditional sessions, as all necessary information is contained within the token itself.

---

## Disadvantages

*   **No Built-in Revocation:** Once a JWT is issued, it remains valid until its expiration. There's no standard, built-in mechanism to "cancel" or "revoke" a token early (e.g., if a user logs out or their account is compromised), requiring workarounds like blacklists or short expiration times with refresh tokens.
*   **Payload Exposure:** The payload is only Base64Url-encoded, not encrypted. This means anyone can read the contents of a JWT. Therefore, sensitive information (like passwords, PII) should *never* be stored directly in the payload.
*   **Token Size:** If too many claims are added to the payload, the token can become large, increasing network overhead with every request.
*   **Security Vulnerabilities:**
    *   **Weak Secrets:** If the secret key used to sign the token is weak or compromised, an attacker can forge tokens.
    *   **Algorithm Confusion:** Older JWT libraries might be vulnerable to attacks where an attacker changes the `alg` header from a strong algorithm (e.g., HS256) to `none`, causing the server to bypass signature verification.
    *   **XSS/CSRF:** If stored insecurely (e.g., in `localStorage`), JWTs are vulnerable to Cross-Site Scripting (XSS) attacks. If stored in regular cookies, they can be vulnerable to Cross-Site Request Forgery (CSRF).

## Common Interview Questions

1.  **What is a JSON Web Token (JWT) and what problem does it solve?**
    *   *Answer:* A JWT is a compact, URL-safe standard for transmitting securely verifiable information between parties. It solves the problem of stateless authentication and authorization in distributed systems by allowing servers to verify user identity without storing session state.

2.  **Explain the three parts of a JWT and their purpose.**
    *   *Answer:* Header (metadata like algorithm and type), Payload (claims or statements about the user/data), and Signature (verifies the token's integrity and authenticity).

3.  **How is a JWT different from a traditional session-based authentication system?**
    *   *Answer:* JWTs are stateless; the server doesn't store session data. Sessions are stateful; the server maintains user session information. JWTs enable scalability and cross-domain usage more easily.

4.  **What are the main security concerns or vulnerabilities associated with JWTs, and how can they be mitigated?**
    *   *Answer:* Concerns include lack of built-in revocation, payload visibility (not encrypted), token theft (XSS), and weak secrets. Mitigation involves short expiration times, refresh tokens, HttpOnly cookies, strong secrets, and avoiding sensitive data in the payload.

5.  **How do you handle JWT revocation or blacklisting?**
    *   *Answer:* Since JWTs are stateless, revocation isn't built-in. Common approaches include maintaining a server-side blacklist of invalidated tokens, using very short-lived access tokens combined with longer-lived refresh tokens (where the refresh token can be revoked), or changing the signing key (which invalidates all previously issued tokens).

## Beginner Mistakes

1.  **Storing JWTs in Local Storage:** While convenient, `localStorage` is vulnerable to Cross-Site Scripting (XSS) attacks. If an attacker injects malicious JavaScript, they can easily access and steal the JWT, leading to session hijacking.
2.  **Putting Sensitive Data in the Payload:** The payload of a JWT is only Base64Url-encoded, not encrypted. This means anyone can decode and read its contents. Beginners often mistakenly put passwords, private user data, or confidential business information directly into the token.
3.  **Not Setting Expiration Times (or setting them too long):** A JWT without an `exp` claim (expiration time) is effectively valid forever. If it's stolen, an attacker has indefinite access. Even a very long expiration time (e.g., days, weeks) poses a significant risk.
4.  **Using Weak or Hardcoded Secrets:** The security of a JWT relies heavily on the secrecy and strength of the signing key. Using a simple, easily guessable, or hardcoded secret (e.g., `123456`, `secret`) makes it trivial for attackers to forge or tamper with tokens.
5.  **Not Validating All Token Parts:** Some beginners might only check the signature but neglect to validate other important claims like `exp` (expiration), `nbf` (not before), `iss` (issuer), or `aud` (audience). This can lead to accepting expired or maliciously issued tokens.
6.  **Sending JWTs over HTTP (not HTTPS):** Even if the token itself is secure, transmitting it over unencrypted HTTP makes it vulnerable to Man-in-the-Middle (MITM) attacks, where an attacker can intercept and steal the token.

---

## Best Practices

1.  **Always Use HTTPS:** Ensure all communication involving JWTs occurs over HTTPS to prevent Man-in-the-Middle (MITM) attacks and token interception.
2.  **Set Short Expiration Times & Use Refresh Tokens:**
    *   **Access Tokens:** Keep access tokens short-lived (e.g., 5-15 minutes). This limits the window of opportunity if a token is stolen.
    *   **Refresh Tokens:** Pair short-lived access tokens with longer-lived refresh tokens. Refresh tokens are stored securely (e.g., HttpOnly cookies) and used only to obtain new access tokens when the old one expires. Refresh tokens *should* be revocable server-side.
3.  **Store Tokens Securely:**
    *   **Web Browsers:** For web applications, store access tokens in `HttpOnly` and `Secure` cookies. This prevents JavaScript from accessing the token (mitigating XSS) and ensures it's only sent over HTTPS.
    *   **Mobile Apps:** Store tokens in the device's secure storage mechanisms (e.g., iOS KeyChain, Android Keystore).
4.  **Use Strong, Unique Secrets/Keys:** The signing key for your JWTs must be long, complex, and securely managed. Never hardcode it in your application code; use environment variables or a secrets management service. For asymmetric algorithms (RSA, ECDSA), protect your private key.
5.  **Never Store Sensitive Data in the Payload:** Remember, the payload is only encoded, not encrypted. Any information in the payload is visible to anyone who has the token. Only include non-sensitive, necessary data (e.g., user ID, roles).
6.  **Validate All Claims Rigorously:** On token receipt, always verify the signature, check the `exp` (expiration), `nbf` (not before), `iss` (issuer), and `aud` (audience) claims. Ensure the algorithm used is the one you expect and not `none`.
7.  **Implement Server-Side Revocation (for Refresh Tokens):** While access tokens are typically not revocable, refresh tokens *must* be. Maintain a database or cache (e.g., Redis) to blacklist compromised refresh tokens or track valid refresh tokens.
8.  **Regularly Rotate Signing Keys:** Periodically change the secret key (for symmetric algorithms) or private key (for asymmetric algorithms) used to sign your JWTs to limit the damage if an old key is compromised.

## Mini Quiz

1.  Which of the following is NOT a part of a JSON Web Token?
    a) Header
    b) Body
    c) Payload
    d) Signature
    **Answer: b) Body**

2.  What does "stateless" mean in the context of JWT authentication?
    a) The server does not store user data.
    b) The server does not store session information.
    c) The token is always valid regardless of time.
    d) The client does not store the token.
    **Answer: b) The server does not store session information.**

3.  Why should sensitive information like passwords or PII (Personally Identifiable Information) NOT be stored in a JWT's payload?
    a) The payload makes the token too large.
    b) The payload is encrypted and cannot be read by anyone.
    c) The payload is only Base64Url-encoded and easily readable by anyone with the token.
    d) The payload is only for technical metadata.
    **Answer: c) The payload is only Base64Url-encoded and easily readable by anyone with the token.**

4.  What is a common strategy to mitigate the risk of stolen JWTs that have a long expiration time?
    a) Encrypting the entire JWT.
    b) Using very short-lived access tokens combined with refresh tokens.
    c) Storing the JWT in `localStorage`.
    d) Using a weaker signing algorithm.
    **Answer: b) Using very short-lived access tokens combined with refresh tokens.**

5.  Which HTTP header is typically used to send a JWT from the client to the server for authentication?
    a) `Content-Type`
    b) `Cookie`
    c) `Authorization`
    d) `Accept`
    **Answer: c) Authorization`** (specifically as `Authorization: Bearer <token>`)

## Practice Task

**Task: Build a Simple JWT-Authenticated API**

Create a basic Node.js (or Python/Flask, etc.) API with two endpoints:

1.  `/login` (POST):
    *   Accepts `username` and `password` in the request body.
    *   If credentials are valid (you can hardcode `user: 'testuser'` and `pass: 'password123'`), generate a JWT.
    *   The JWT payload should include `userId`, `username`, and a `role` (e.g., `user`).
    *   The token should expire in `1h`.
    *   Return the JWT in the response.
2.  `/profile` (GET):
    *   This endpoint should be **protected by JWT authentication**.
    *   It should expect a JWT in the `Authorization: Bearer <token>` header.
    *   Verify the token: check its signature and expiration.
    *   If the token is valid, extract the `username` from the payload and return a welcome message like "Welcome, [username]! This is your profile data."
    *   If the token is invalid (missing, expired, or tampered), return an appropriate error (e.g., 401 Unauthorized, 403 Forbidden).

**Bonus Challenges:**

*   Implement a `/logout` endpoint that effectively "invalidates" the token (you can simulate this by telling the user to discard it, or for advanced users, implement a simple blacklist).
*   Add another protected endpoint `/admin` that only grants access if the token's payload contains `role: 'admin'`. Modify your `/login` to issue an admin token for a specific user (e.g., `admin: 'adminpass'`).

This task will give you hands-on experience with JWT generation, verification, and protected route implementation.

## Summary

JWTs provide a robust, compact, and secure method for transmitting information between parties, predominantly used for stateless authentication and authorization in modern web and mobile applications. By leveraging a digitally signed, self-contained token, they enable scalable, distributed systems where servers don't need to maintain session state. Composed of a header, payload, and signature, JWTs ensure data integrity and authenticity. While offering significant advantages in scalability and cross-platform compatibility, it's crucial to be aware of their limitations, such as the lack of built-in revocation and the non-encrypted nature of their payload. Adhering to best practices like using HTTPS, short-lived tokens with refresh tokens, secure storage, and strong secrets is paramount to building secure and reliable JWT-based systems. Understanding JWTs is a fundamental skill for any contemporary software engineer.
