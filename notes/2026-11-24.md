# JWT

## What is it?

JWT, or JSON Web Token, is a compact, URL-safe means of representing claims to be transferred between two parties. It's essentially a digitally signed piece of information, primarily used for authentication and authorization. Think of it like a secure, tamper-proof ID card for your application users. When a user logs in, the server issues a JWT containing user-specific data (claims) and signs it with a secret key. This token is then sent back to the user, who includes it with subsequent requests. The server can quickly verify the token's authenticity and integrity without repeated database lookups. A JWT has three parts: a header, a payload, and a signature, separated by dots (`.`).

---

## Why is it important?

JWTs are fundamental in modern web development for several key reasons:

*   **Stateless Authentication:** Unlike traditional session-based systems that store state on the server, JWTs are self-contained. The server doesn't need to maintain session information, making applications highly scalable, especially for distributed systems and microservices.
*   **Authorization:** JWTs can carry claims (e.g., user roles, permissions) directly within the token. This allows servers to quickly determine what a user is authorized to do without extra database queries.
*   **Information Exchange:** They provide a secure way to transmit information between parties. The digital signature ensures the data's integrity and verifies the sender's authenticity.
*   **Cross-Domain Single Sign-On (SSO):** A single JWT can be issued by an authentication server and used across multiple related applications or domains, streamlining the user experience.
*   **API and Mobile Authentication:** Their compact nature and stateless property make JWTs an ideal choice for securing RESTful APIs and mobile application backends.

---

## Real World Example

Consider logging into an e-commerce website:

1.  **Login:** You enter your username and password on the website. Your browser sends these credentials to the e-commerce server.
2.  **Token Issuance:** The server verifies your credentials. If valid, it generates a JWT containing your user ID, perhaps your loyalty status, and an expiry time. The server then signs this token with a secret key it keeps private.
3.  **Token Storage:** The server sends this JWT back to your browser. Your browser stores it, typically in an HTTP-only cookie or `sessionStorage`.
4.  **Subsequent Requests:** Now, every time you add an item to your cart, proceed to checkout, or view your order history, your browser automatically attaches this JWT to the request (usually in the `Authorization: Bearer <token>` header).
5.  **Token Verification:** The e-commerce server receives the request with the JWT. It takes the token, verifies its signature using its secret key, and checks its expiry. If the token is valid, the server trusts your identity and permissions without needing to hit the database to confirm who you are for every action.

This process enables efficient, secure, and stateless communication, enhancing scalability and responsiveness.

## Syntax / Example

A JWT is a compact string structured as `Header.Payload.Signature`. Each part is Base64Url-encoded.

Let's dissect its components:

**1. Header (JOSE Header)**
The header typically defines the token type (`JWT`) and the signing algorithm (`alg`) used, e.g., HMAC SHA256 (`HS256`).

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```
Base64Url-encoded example: `eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9`

**2. Payload (JWT Claims)**
The payload contains "claims," which are statements about the entity (user) and additional metadata.
*   **Registered Claims:** Predefined (e.g., `iss` for issuer, `exp` for expiration, `sub` for subject).
*   **Public Claims:** Custom claims, publicly defined.
*   **Private Claims:** Custom claims agreed upon by the parties.

```json
{
  "sub": "user123",
  "name": "Jane Doe",
  "role": "admin",
  "iat": 1678886400, // Issued at (timestamp)
  "exp": 1678890000  // Expiration time (timestamp, 1 hour later)
}
```
Base64Url-encoded example: `eyJzdWIiOiJ1c2VyMTIzIiwibmFtZSI6IkphbmUgRG9lIiwicm9sZSI6ImFkbWluIiwiaWF0IjoxNjc4ODg2NDAwLCJleHAiOjE2Nzg4OTAwMDB9`

**3. Signature**
The signature ensures the token's integrity. It's created by taking the encoded header, the encoded payload, a secret key (known only to the server), and the specified algorithm, then hashing them.

`HMACSHA256( base64UrlEncode(header) + "." + base64UrlEncode(payload), secret_key )`

**Example Complete JWT (concatenated):**
`eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1c2VyMTIzIiwibmFtZSI6IkphbmUgRG9lIiwicm9sZSI6ImFkbWluIiwiaWF0IjoxNjc4ODg2NDAwLCJleHAiOjE2Nzg4OTAwMDB9.some_generated_signature_string`

When received, the server reconstructs the signature using its secret key. If it matches the token's signature, the token is verified as authentic and untampered.

## Advantages

*   **Statelessness & Scalability:** Eliminates server-side session storage, allowing easy horizontal scaling and microservices architecture.
*   **Self-Contained:** Contains all necessary user information, reducing the need for repeated database lookups.
*   **Cross-Domain Compatibility:** Facilitates Single Sign-On (SSO) across different applications and domains.
*   **Security:** Digitally signed to ensure authenticity and integrity of claims.
*   **Compact:** Small size allows efficient transmission via URL, POST parameters, or HTTP headers.
*   **Standardized:** An open, industry-standard (RFC 7519) for secure information exchange.

---

## Disadvantages

*   **No Easy Revocation:** Once issued, a JWT is valid until it expires. Revoking a compromised token before expiry requires additional mechanisms (e.g., blacklists, short expiry).
*   **Token Size:** Too many claims can increase token size, adding to request overhead.
*   **Security Risks if Mismanaged:** Vulnerable to XSS if stored insecurely (e.g., `localStorage`).
*   **No Encryption by Default:** JWTs are signed but not encrypted. Their payload is readable, so sensitive data should not be included. JWE (JSON Web Encryption) is required for encryption.
*   **Complexity with Refresh Tokens:** Implementing refresh tokens to handle revocation and improve user experience adds architectural complexity.

## Common Interview Questions

1.  **What is the primary purpose of a JWT?**
    *   *Answer:* To securely transmit information between parties, primarily for stateless authentication and authorization.
2.  **Explain the three parts of a JWT.**
    *   *Answer:* Header (algorithm/type), Payload (claims/data), and Signature (verification).
3.  **Are JWTs encrypted?**
    *   *Answer:* No, JWTs are encoded (Base64Url) and signed, not encrypted by default. Their content is readable.
4.  **What are the main advantages of JWTs over traditional session-based authentication?**
    *   *Answer:* Statelessness, scalability, cross-domain support, and reduced database lookups.
5.  **How do you handle JWT revocation?**
    *   *Answer:* Strategies include short-lived access tokens with refresh tokens, blacklisting compromised tokens, or enforcing very short expiry times.

## Beginner Mistakes

*   **Storing JWTs in `localStorage`:** Highly vulnerable to Cross-Site Scripting (XSS) attacks. Malicious JavaScript can easily steal the token. HTTP-only cookies are generally safer for access tokens.
*   **Putting Sensitive Data in the Payload:** JWT payloads are only encoded, not encrypted. Anyone who intercepts the token can decode and read its contents. Never include confidential information directly.
*   **Using Weak Secrets for Signing:** A weak secret makes the signature vulnerable to brute-force attacks, allowing attackers to forge valid tokens. Always use long, complex, cryptographically secure secrets.
*   **Not Setting Expiry Times (`exp` claim):** Tokens that never expire (or have very long expiry) are a major security risk. If stolen, they grant perpetual access. Always set reasonable expiry times.
*   **Ignoring HTTPS:** Transmitting JWTs over unencrypted HTTP leaves them vulnerable to Man-in-the-Middle attacks, where tokens can be intercepted and stolen.
*   **Not Validating All Claims:** Failing to validate critical claims like `exp`, `iss` (issuer), and `aud` (audience) can lead to accepting expired, forged, or improperly issued tokens.

---

## Best Practices

*   **Always Use HTTPS/SSL/TLS:** Encrypt all communications to protect JWTs in transit from eavesdropping and Man-in-the-Middle attacks.
*   **Use Strong, Unique Signing Secrets:** Generate long, random, cryptographically secure keys for signing. Store them securely (e.g., environment variables, secret management services), and never hardcode them.
*   **Implement Short-Lived Access Tokens with Refresh Tokens:** Issue access tokens with a short expiry (e.g., 5-15 minutes) for API access. Use separate, long-lived refresh tokens (stored securely in HTTP-only cookies) to obtain new access tokens, allowing easier revocation if compromised.
*   **Store Access Tokens Securely:**
    *   For browser apps: Prefer HTTP-only, `Secure` cookies to protect against XSS. Implement CSRF protection (e.g., anti-CSRF tokens).
    *   For mobile/SPAs: Consider `sessionStorage` or in-memory storage. Avoid `localStorage` for access tokens.
*   **Validate All Claims Thoroughly:** On the server, always verify the token's signature, `exp`, `iat`, `iss`, and `aud` claims to ensure the token's authenticity, validity, and intended use.
*   **Avoid Sensitive Data in Payload:** Only include non-sensitive, necessary information. If sensitive data must be transmitted, use JWE (JSON Web Encryption).
*   **Implement Revocation Mechanisms (When Necessary):** For critical applications, implement token blacklisting/denylisting for compromised tokens or immediate logout.
*   **Audience Restriction (`aud` claim):** Specify which services or applications a token is intended for to prevent its misuse in unintended contexts.

## Practice Task

**Task: Build a Basic JWT-Secured API**

Create a simple application with a Node.js/Express backend that implements JWT-based authentication and a protected route.

**Backend (Node.js/Express):**

1.  Initialize a new Node.js project (`npm init -y`) and install `express` and `jsonwebtoken`.
2.  Create an Express server.
3.  Implement a `/login` endpoint (POST request):
    *   Accept `username` and `password` in the request body.
    *   If credentials match `testuser`/`testpassword`, generate a JWT using `jsonwebtoken.sign()`. Include a `userId` and `role` claim in the payload and set an expiry of 1 hour.
    *   Send the generated JWT back in the response.
    *   For invalid credentials, return a 401 Unauthorized error.
4.  Implement a JWT verification middleware:
    *   Extract the token from the `Authorization` header (`Bearer <token>`).
    *   Verify the token using `jsonwebtoken.verify()` with your secret key.
    *   If valid, attach the decoded payload to the request object (e.g., `req.user`) and call `next()`.
    *   If invalid or missing, return a 401 Unauthorized or 403 Forbidden error.
5.  Create a `/protected` endpoint (GET request) that uses your JWT verification middleware:
    *   If access is granted, return a message like "Welcome to the protected resource, [username]!" (using `req.user.username` from the decoded token).

**Learning Outcome:** This task will provide hands-on experience with JWT generation, signing, verification, and implementing secure API routes.

## Summary

JSON Web Tokens (JWTs) are a standardized, compact, and secure method for transmitting information between parties, fundamentally used for stateless authentication and authorization in modern web applications. They consist of a Base64Url-encoded header, payload, and a cryptographic signature, allowing servers to verify identity and permissions without storing session data. While offering advantages like scalability, cross-domain support, and reduced database lookups, it's crucial to address considerations such as token revocation and secure storage to mitigate vulnerabilities like XSS. Adhering to best practices—including HTTPS, strong secrets, short-lived tokens with refresh tokens, and thorough claim validation—is paramount for the secure and effective deployment of JWTs in any distributed system.
