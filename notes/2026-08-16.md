# JWT

## What is it?

JWT, or JSON Web Token, is an open standard (RFC 7519) that defines a compact and self-contained way for securely transmitting information between parties as a JSON object. This information can be verified and trusted because it is digitally signed. JWTs are often used for authentication and authorization in web applications, particularly in stateless API scenarios.

A JWT fundamentally consists of three parts, separated by dots (`.`):
1.  **Header**: Contains metadata about the token itself, typically the type of token (JWT) and the signing algorithm used (e.g., HMAC SHA256 or RSA).
2.  **Payload**: Contains the "claims" – statements about an entity (typically, the user) and additional data. Claims can be registered (standardized, like `iss` for issuer, `exp` for expiration), public (custom but collision-resistant), or private (custom, agreed upon by sender/receiver).
3.  **Signature**: Created by taking the encoded header, the encoded payload, a secret key, and the algorithm specified in the header, and then signing it. This signature is used to verify that the sender of the JWT is who it says it is and to ensure that the message hasn't been tampered with.

The first two parts (Header and Payload) are Base64Url encoded, not encrypted, meaning their content is easily readable. It is the signature that provides the security, ensuring integrity and authenticity.

---

## Why is it important?

JWTs have become a cornerstone of modern web and API security due to several key advantages:

*   **Stateless Authentication:** Unlike traditional session-based authentication where the server stores session information (e.g., in a database or memory), JWTs allow for stateless authentication. The server doesn't need to store session data; instead, it verifies the token's signature and claims on each request. This significantly improves scalability, especially for microservices architectures and distributed systems, as any server can validate the token.
*   **Decentralized Authorization:** A JWT issued by one service (e.g., an authentication service) can be validated and trusted by other services (e.g., resource APIs) without direct communication between them, as long as they share the same secret key or have access to the public key for validation.
*   **Mobile and Single Page Application (SPA) Friendly:** JWTs are easily transmitted in HTTP headers (`Authorization: Bearer <token>`) making them ideal for mobile applications and SPAs, which often communicate with backend APIs.
*   **Secure Information Exchange:** The digitally signed nature of JWTs ensures that the information within the token (claims) has not been tampered with since it was issued, providing data integrity and authenticity.
*   **Reduced Database Load:** For every authenticated request, the server can retrieve user information directly from the token's payload (e.g., user ID, roles) without needing to query a database, reducing latency and server load.

## Real World Example

Imagine a user logging into a modern web application, like an online banking portal or a social media platform, built with a separate frontend (e.g., React, Angular, Vue.js) and a backend API (e.g., Node.js, Python Flask, Java Spring Boot).

1.  **Login:** The user enters their username and password into the frontend application.
2.  **Authentication Request:** The frontend sends these credentials to the backend authentication API.
3.  **Token Issuance:** The backend API verifies the credentials. If valid, it generates a JWT containing claims like the `userId`, `username`, and `roles`. It then signs this JWT with a secret key and sends it back to the frontend.
4.  **Token Storage:** The frontend receives the JWT and stores it, typically in `localStorage`, `sessionStorage`, or an `HttpOnly` cookie.
5.  **Subsequent Requests:** Whenever the user wants to access a protected resource (e.g., view their profile, make a transaction), the frontend attaches the stored JWT to the `Authorization` header of every HTTP request: `Authorization: Bearer <JWT>`.
6.  **Token Verification:** When the backend API receives a request with a JWT, it first verifies the token's signature using the same secret key. If the signature is valid, it then checks other claims like the expiration time (`exp`) to ensure the token hasn't expired.
7.  **Resource Access:** If the JWT is valid and unexpired, the backend grants access to the requested resource. It can also use claims from the payload (e.g., `userId`, `roles`) to determine specific access permissions without needing to query a database for user details.

This process allows the user to remain logged in and securely access protected resources without the server needing to maintain a server-side session, making the application highly scalable and efficient.

## Syntax / Example

A JWT typically looks like three Base64Url-encoded strings separated by dots:

`eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c`

Let's break down its components conceptually and then with a simple Node.js example using the `jsonwebtoken` library.

### Decoding the Parts (Conceptual)

1.  **Header (Base64Url-decoded):**
    ```json
    {
      "alg": "HS256", // Algorithm used for signing (HMAC SHA256)
      "typ": "JWT"    // Type of token
    }
    ```

2.  **Payload (Base64Url-decoded):**
    ```json
    {
      "sub": "1234567890", // Subject: User ID
      "name": "John Doe",  // Public claim: User's name
      "iat": 1516239022,   // Issued At: Timestamp
      "exp": 1516242622    // Expiration Time (e.g., 1 hour after iat)
    }
    ```
    *Note: `exp` (expiration time) and `iat` (issued at) are standard registered claims.*

3.  **Signature:** This is a hash generated using the encoded header, encoded payload, a secret key, and the algorithm specified in the header. It ensures the token's integrity.

### Code Example (Node.js with `jsonwebtoken` library)

This example demonstrates how to create and verify a JWT.

First, install the library:
`npm install jsonwebtoken`

```javascript
const jwt = require('jsonwebtoken');

// A strong, secret key is crucial for security.
// In a real application, this should be stored securely (e.g., environment variable).
const SECRET_KEY = 'your_super_secret_key_that_no_one_should_ever_guess_or_know';

// 1. Creating a JWT
function createToken(payloadData) {
  // `jwt.sign` takes the payload, secret key, and optional options.
  // `expiresIn` is a common option to define the token's validity period.
  const token = jwt.sign(payloadData, SECRET_KEY, { expiresIn: '1h' });
  return token;
}

// 2. Verifying a JWT
function verifyToken(token) {
  try {
    // `jwt.verify` takes the token, secret key, and optional options.
    // It decodes the token and verifies its signature and claims (like expiration).
    const decoded = jwt.verify(token, SECRET_KEY);
    console.log('Token verified successfully. Decoded payload:', decoded);
    return decoded;
  } catch (err) {
    // Handle various errors like 'TokenExpiredError', 'JsonWebTokenError' (invalid signature)
    console.error('JWT verification failed:', err.message);
    return null;
  }
}

// --- Usage Example ---

// Define the payload for our token
const userPayload = {
  userId: 'user123',
  username: 'alice',
  roles: ['user', 'editor']
};

console.log('--- Creating Token ---');
const generatedToken = createToken(userPayload);
console.log('Generated JWT:', generatedToken);
console.log('\n');

console.log('--- Verifying Token ---');
// Verify the generated token
verifyToken(generatedToken);
console.log('\n');

// Example of an invalid token (e.g., tampered or wrong secret)
const tamperedToken = generatedToken.slice(0, -5) + 'xxxxx'; // Simulate tampering
console.log('--- Verifying Tampered Token ---');
verifyToken(tamperedToken);
console.log('\n');

// Example of a token with an invalid signature (using a different secret)
const WRONG_SECRET = 'this_is_a_wrong_secret';
try {
  jwt.verify(generatedToken, WRONG_SECRET);
} catch (err) {
  console.log('--- Verifying with Wrong Secret ---');
  console.error('JWT verification failed (wrong secret):', err.message);
}
```

## Advantages

*   **Statelessness & Scalability:** Eliminates the need for server-side session storage, making APIs highly scalable and easy to distribute across multiple servers or microservices.
*   **Decentralized Authorization:** Enables different services to independently verify tokens issued by a trusted authentication server, fostering a decoupled architecture.
*   **Performance:** Can reduce database lookups for session information on every request, as user data (claims) is directly available in the token.
*   **Mobile & SPA Friendly:** Easily passed in HTTP `Authorization` headers, making them ideal for modern web and mobile applications.
*   **Information Exchange:** Provides a standardized and secure way to exchange verifiable claims between parties.
*   **Flexibility:** Can be signed using various algorithms (HMAC, RSA, ECDSA), allowing for different security and operational requirements.

---

## Disadvantages

*   **Token Invalidation/Revocation:** Once a JWT is issued, it's generally valid until its expiration time. Revoking an active token (e.g., if a user logs out, changes password, or is banned) before its natural expiry is not straightforward and often requires implementing a blacklist or similar mechanism.
*   **Payload Size:** While compact, the token's size can grow if too many claims are added to the payload. This increases the size of every request, potentially affecting performance for very large tokens.
*   **Security of Secret Key:** The entire security of signed JWTs (JWS) hinges on the secrecy of the private key (for HMAC) or the private key pair (for RSA/ECDSA). If compromised, an attacker can forge valid tokens.
*   **No Built-in Refresh Mechanism:** JWTs themselves don't provide a standard mechanism for refreshing tokens. This typically requires implementing a separate "refresh token" flow to securely obtain new access tokens.
*   **Storage Vulnerabilities:** Storing JWTs in client-side storage like `localStorage` or `sessionStorage` can expose them to Cross-Site Scripting (XSS) attacks, where malicious scripts can steal the token.

## Beginner Mistakes

*   **Storing JWTs in `localStorage`:** While convenient, `localStorage` is vulnerable to XSS attacks. If an attacker injects a malicious script, they can easily access and steal the user's JWT, leading to session hijacking.
*   **Using Weak or Hardcoded Secret Keys:** A weak secret key makes it easy for an attacker to brute-force or guess the key, allowing them to forge or tamper with tokens. Hardcoding the key directly in the codebase is also a security risk.
*   **Putting Sensitive Data in the Payload:** The payload is only Base64Url encoded, not encrypted. Anyone can decode it. Never store sensitive information like unhashed passwords, credit card numbers, or personally identifiable information (PII) directly in the JWT payload.
*   **Not Validating All Aspects of the Token:** Failing to validate the signature, expiration (`exp`), issuer (`iss`), or audience (`aud`) claims can lead to security vulnerabilities where invalid or expired tokens are accepted.
*   **Long-Lived Access Tokens Without Refresh Tokens:** Issuing JWTs with very long expiration times (e.g., months or years) increases the window of opportunity for an attacker if the token is compromised. It's better to use short-lived access tokens combined with refresh tokens.
*   **Exposing the Secret Key:** The secret key used to sign JWTs should be treated like a password and kept highly confidential. Committing it to version control or exposing it in client-side code is a critical error.

## Best Practices

*   **Use Strong, Securely Stored Secret Keys:** Generate strong, random, long secret keys (at least 32 bytes for HS256) and store them securely, preferably in environment variables or a dedicated key management service, not in the codebase.
*   **Implement Short-Lived Access Tokens and Long-Lived Refresh Tokens:** Use short expiration times (e.g., 5-15 minutes) for access tokens. When an access token expires, use a separate, longer-lived refresh token (stored in an `HttpOnly` cookie) to obtain a new access token. This limits the window of attack if an access token is compromised.
*   **Store Access Tokens Securely:**
    *   For SPAs: Consider storing access tokens in memory (and re-fetching on page refresh) or in `HttpOnly` cookies (requires CSRF protection). Avoid `localStorage` for sensitive tokens.
    *   For mobile apps: Use secure storage provided by the operating system (e.g., iOS KeyChain, Android Keystore).
*   **Always Use HTTPS/SSL:** Ensure all communication between client and server is encrypted using HTTPS to prevent Man-in-the-Middle (MITM) attacks from intercepting tokens.
*   **Validate All Relevant Claims:** On the server-side, always validate the `exp` (expiration), `nbf` (not before), `iss` (issuer), and `aud` (audience) claims in addition to the signature.
*   **Avoid Sensitive Data in Payload:** Do not store any sensitive, unencrypted data in the JWT payload. If sensitive data is required, encrypt it within the payload using JWE (JSON Web Encryption) or retrieve it from a secure backend service using the token's `userId` claim.
*   **Implement Token Revocation (Blacklisting) When Necessary:** For critical events like user logout, password change, or account compromise, implement a blacklist mechanism to invalidate active JWTs before their natural expiration. This involves storing invalid tokens (or their IDs) in a fast-access database (e.g., Redis).
*   **Regularly Rotate Keys:** Periodically change your secret keys to mitigate the risk of long-term compromise.

## Practice Task

**Build a Simple JWT-Authenticated API:**

Create a basic backend API (e.g., using Node.js with Express, Python with Flask, or Java with Spring Boot) that implements JWT-based authentication.

1.  **`/login` Endpoint (POST):**
    *   Accepts `username` and `password` in the request body.
    *   If credentials are valid (you can hardcode them for this task, e.g., user: `testuser`, pass: `password123`), generate a JWT with a `userId` and `username` claim, set an `expiresIn` of 1 hour.
    *   Return the generated JWT in the response body.
2.  **`/protected` Endpoint (GET):**
    *   Requires a valid JWT in the `Authorization: Bearer <token>` header.
    *   Implement middleware to verify the JWT (signature, expiration).
    *   If the token is valid, respond with a success message and potentially some user data retrieved from the token's payload (e.g., "Welcome, [username]! This is protected data.").
    *   If the token is missing, invalid, or expired, return an appropriate error message (e.g., 401 Unauthorized, 403 Forbidden).

## Summary

JSON Web Tokens (JWTs) are a robust, open-standard method for securely transmitting information between parties. They consist of a header, payload, and signature, enabling stateless authentication and authorization, which is crucial for scalable APIs, microservices, and modern web applications (SPAs, mobile apps). While offering significant advantages in scalability and efficiency, JWTs come with considerations such as token invalidation challenges, the need for secure secret key management, and careful client-side storage practices. By adhering to best practices like using short-lived access tokens with refresh tokens, strong secret keys, HTTPS, and avoiding sensitive data in payloads, developers can leverage JWTs to build secure and performant authentication systems.
