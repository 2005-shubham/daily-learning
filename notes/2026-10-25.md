# JWT

## What is it?

JWT, short for JSON Web Token, is an open standard (RFC 7519) that defines a compact and self-contained way for securely transmitting information between parties as a JSON object. Think of it as a digitally signed ID card for your application's users or services.

At its core, a JWT is a string made up of three parts, separated by dots (`.`), each Base64Url-encoded:

1.  **Header**: Contains metadata about the token itself, like the type of token (JWT) and the signing algorithm used (e.g., HMAC SHA256 or RSA).
2.  **Payload**: Contains the "claims" – statements about an entity (typically, the user) and additional data. Claims can include user ID, roles, expiration time, issuer, audience, etc. *Crucially, the payload is NOT encrypted; it is only encoded. Therefore, no sensitive information should ever be stored here.*
3.  **Signature**: This is the security guardian. It's created by taking the encoded header, the encoded payload, a secret key (known only to the server), and the algorithm specified in the header, then signing them. This signature is used to verify that the sender of the JWT is who it claims to be and that the message hasn't been tampered with.

When a client receives a JWT, it can pass it along with subsequent requests. The server can then verify the token's authenticity using the signature and the secret key, ensuring the data hasn't been altered and that the token was issued by a trusted source, without needing to hit a database every time.

---

## Why is it important?

JWTs have become a cornerstone in modern web development, particularly for building scalable and secure applications. Their importance stems from several key benefits:

*   **Stateless Authentication**: Traditional web sessions often require servers to store session information (like session IDs) in memory or a database. With JWTs, the server doesn't need to maintain session state. The token itself contains all the necessary user information and is self-contained. This makes applications highly scalable, as any server can process any request without needing to share session data.
*   **API Security**: JWTs provide a robust mechanism for securing APIs. Once a user authenticates, they receive a JWT. This token is then included in the `Authorization` header of subsequent API requests. The API can validate the token and grant access to resources based on the claims within it (e.g., user roles, permissions).
*   **Microservices Architecture**: In a microservices environment, where multiple services need to communicate and authenticate users, JWTs simplify the process. A single authentication service can issue a JWT, and other microservices can independently validate it without needing to consult the central authentication service for every request, as long as they share the same secret key (or public key for asymmetric signing).
*   **Reduced Server Load**: By offloading session management to the client (via the JWT), servers can reduce memory usage and database lookups associated with traditional session storage.
*   **Cross-Domain Authentication (CORS)**: JWTs make it easier to handle authentication across different domains (e.g., a frontend application on `app.example.com` making API calls to `api.example.com`). Since the token is passed in the request header, CORS issues related to cookies are often circumvented.
*   **Mobile Application Integration**: JWTs are particularly well-suited for mobile applications, where traditional cookie-based sessions can be cumbersome. Mobile clients can easily store and send JWTs in HTTP headers.

## Real World Example

Imagine you're building a popular online e-commerce platform with a user login system.

1.  **User Logs In**: A user enters their username and password into your website or mobile app.
2.  **Authentication Server**: Your backend server receives these credentials, verifies them against its database (e.g., checks if the password hash matches).
3.  **JWT Issuance**: If the credentials are valid, the server creates a JWT. The payload of this token might contain the user's ID, their role (e.g., `customer`), and an expiration time (e.g., 1 hour from now). It then signs this token using a secret key known only to the server.
4.  **Token Sent to Client**: The server sends this JWT back to the user's browser or mobile app.
5.  **Client Stores Token**: The client-side application (e.g., a React app or an iOS app) stores this JWT (e.g., in `localStorage`, `sessionStorage`, or secure storage for mobile).
6.  **Subsequent Requests**: When the user wants to perform an action that requires authentication, such as adding an item to their cart, viewing their order history, or updating their profile, the client attaches the JWT to the `Authorization` header of the HTTP request (e.g., `Authorization: Bearer <your_jwt_here>`).
7.  **Server Verifies Token**: The backend server receives the request. Before processing it, it inspects the `Authorization` header, extracts the JWT, and verifies its signature using the same secret key. It also checks the token's expiration time and other claims.
8.  **Access Granted/Denied**: If the token is valid and not expired, the server knows the request is coming from an authenticated user and can safely extract the user's ID from the payload to fetch their specific data (e.g., their cart contents). If the token is invalid or expired, the server denies access, prompting the user to log in again.

This flow allows the user to make multiple authenticated requests without re-entering their credentials every time, and the server doesn't need to maintain a persistent session for them.

## Syntax / Example

A JWT is a string consisting of three parts separated by dots (`.`).

**Structure:** `header.payload.signature`

Let's look at an example of a decoded JWT:

**1. Header (Encoded):** `eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9`
**Decoded Header:**
```json
{
  "alg": "HS256", // Algorithm used for signing (HMAC SHA256)
  "typ": "JWT"    // Type of token
}
```

**2. Payload (Encoded):** `eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyLCJleHAiOjE2MTYyNDI2MjJ9`
**Decoded Payload:**
```json
{
  "sub": "1234567890", // Subject (user ID)
  "name": "John Doe",  // User's name
  "iat": 1516239022,   // Issued At (Unix timestamp)
  "exp": 1616242622    // Expiration Time (Unix timestamp)
}
```
*(Note: `iat` and `exp` are standard registered claims. You can add custom claims too.)*

**3. Signature:** A hash generated from the encoded header, encoded payload, a secret, and the algorithm.
Example (truncated for brevity): `S6-S9t0...`

**Full JWT (example):**
`eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyLCJleHAiOjE2MTYyNDI2MjJ9.S6-S9t0fD-X1y2g2S7_h1Z9m_z_y_x_h_g_j_k_l_p_o_i_u_y_t_r_e_w_q_a_z_x_c_v_b_n_m`

**Code Example (Node.js with `jsonwebtoken` library):**

**1. Installing the library:**
```bash
npm install jsonwebtoken
```

**2. Issuing a JWT:**
```javascript
const jwt = require('jsonwebtoken');

// A secret key for signing the token. Keep this secure and strong!
const JWT_SECRET = 'your_super_secret_key_for_jwt_signing_12345!@#$'; // Use a strong, random key in production

// User data to include in the payload
const userData = {
  userId: 'user123',
  email: 'john.doe@example.com',
  role: 'admin'
};

// Options for signing
const options = {
  expiresIn: '1h', // Token expires in 1 hour
  issuer: 'your-app-name.com', // Who issued the token
  audience: 'your-frontend-app.com' // Who the token is intended for
};

// Sign the token
try {
  const token = jwt.sign(userData, JWT_SECRET, options);
  console.log('Generated JWT:', token);
  // In a real application, you would send this token back to the client
} catch (error) {
  console.error('Error generating JWT:', error.message);
}
```

**3. Verifying a JWT:**
```javascript
const jwt = require('jsonwebtoken');

const JWT_SECRET = 'your_super_secret_key_for_jwt_signing_12345!@#$'; // Must be the same secret used for signing

// Assume this token was received from the client
const receivedToken = 'eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VySWQiOiJ1c2VyMTIzIiwiZW1haWwiOiJqb2huLmRvZUBleGFtcGxlLmNvbSIsInJvbGUiOiJhZG1pbiIsImlhdCI6MTY3ODg4NjQwMCwiZXhwIjoxNjc4ODkwMDAwLCJpc3MiOiJ5b3VyLWFwcC1uYW1lLmNvbSIsImF1ZCI6InlvdXItZnJvbnRlbmQtYXBwLmNvbSJ9.YOUR_SIGNATURE_HERE'; // Replace with an actual generated token

try {
  const decoded = jwt.verify(receivedToken, JWT_SECRET, {
    issuer: 'your-app-name.com',
    audience: 'your-frontend-app.com'
  });
  console.log('Decoded JWT Payload:', decoded);
  // Access user data: decoded.userId, decoded.email, decoded.role
  // You can now proceed with the request, knowing the user is authenticated and authorized
} catch (error) {
  console.error('Error verifying JWT:', error.message);
  // Handle invalid token (e.g., token expired, invalid signature)
}
```
*(Note: For asymmetric algorithms like RSA, the signing uses a private key, and verification uses the corresponding public key.)*

## Advantages

*   **Stateless and Scalable**: Servers don't need to store session information, making applications easier to scale horizontally across multiple servers.
*   **Self-Contained**: All necessary user information (claims) is embedded within the token, reducing the need for database lookups on every request.
*   **Compact**: JWTs are small and can be sent easily through URL, POST parameter, or inside an HTTP header.
*   **Mobile-Friendly**: Works seamlessly with mobile applications and APIs, where cookie-based sessions can be problematic.
*   **Standardized**: Adheres to an open standard (RFC 7519), promoting interoperability across different programming languages and platforms.
*   **Cross-Domain/CORS Friendly**: Since tokens are passed in headers, they bypass same-origin policy issues that often affect traditional cookie-based authentication.

---

## Disadvantages

*   **No Built-in Revocation**: Once a JWT is issued, it's valid until its expiration time. There's no standard way to "revoke" or blacklist a token prematurely (e.g., if a user logs out, changes password, or a token is compromised). This often requires custom implementation (e.g., a blacklist on the server-side).
*   **Token Size**: While compact, adding too many claims to the payload can increase the token's size, leading to slightly increased overhead in network requests.
*   **Security of Secret Key**: If the secret key used to sign the token is compromised, an attacker can forge valid tokens, completely undermining the security of the application.
*   **No Encryption by Default**: The payload is only Base64Url-encoded, not encrypted. Sensitive information should never be stored directly in the payload as it can be easily read. Encryption (JWE - JSON Web Encryption) is a separate standard.
*   **Vulnerability to XSS/CSRF (if not handled correctly)**: If JWTs are stored in `localStorage` or `sessionStorage`, they are vulnerable to Cross-Site Scripting (XSS) attacks. If stored in insecure cookies, they can be vulnerable to Cross-Site Request Forgery (CSRF) attacks.

## Common Interview Questions

1.  **What is a JWT and what problem does it solve?**
    *   *Answer:* A JSON Web Token is a compact, URL-safe means of representing claims to be transferred between two parties. It solves the problem of stateless authentication, allowing servers to verify client identity without needing to store session data.

2.  **Explain the three parts of a JWT and what each contains.**
    *   *Answer:* Header (algorithm, token type), Payload (claims like user ID, roles, expiration), and Signature (used to verify the token's integrity and authenticity).

3.  **How is a JWT secured? Is the payload encrypted?**
    *   *Answer:* A JWT is secured by its digital signature, which prevents tampering and verifies the issuer. The payload is Base64Url-encoded, *not encrypted*, meaning its contents can be read. Sensitive data should not be stored in the payload.

4.  **What are the main advantages and disadvantages of using JWTs compared to traditional session-based authentication?**
    *   *Answer:* Advantages include statelessness, scalability, cross-domain compatibility, and reduced server load. Disadvantages include no inherent revocation mechanism, potential token size issues, and reliance on the security of the secret key.

5.  **How do you handle JWT revocation, given that they are inherently stateless?**
    *   *Answer:* Common strategies include maintaining a server-side blacklist for compromised or logged-out tokens, setting very short expiration times combined with refresh tokens, or implementing a token rotation mechanism.

6.  **Where should JWTs ideally be stored on the client-side, and why?**
    *   *Answer:* For access tokens, secure HTTP-only cookies are often recommended to mitigate XSS risks, as JavaScript cannot access them. For refresh tokens, which have longer lifespans, even more secure storage like encrypted browser storage or dedicated mobile secure storage is preferred, also often via HTTP-only cookies. Storing in `localStorage` is generally discouraged due to XSS vulnerability.

## Beginner Mistakes

*   **Storing Sensitive Information in the Payload**: The payload is only encoded, not encrypted. Any data put there is publicly readable. Beginners often mistakenly include passwords, social security numbers, or other confidential data.
*   **Using Weak Secrets**: Generating tokens with easily guessable or short secret keys makes them highly vulnerable to brute-force attacks on the signature.
*   **Not Setting Expiration Times (`exp`)**: Issuing tokens that never expire creates a security loophole. If such a token is compromised, it remains valid indefinitely, posing a persistent threat.
*   **Not Validating All Claims**: Failing to validate claims like `exp` (expiration), `nbf` (not before), `iss` (issuer), and `aud` (audience) can lead to accepting expired, future-dated, or incorrectly issued tokens.
*   **Storing JWTs in `localStorage`**: While convenient, `localStorage` is highly susceptible to Cross-Site Scripting (XSS) attacks. If an attacker injects malicious JavaScript, they can easily steal the JWT and impersonate the user.
*   **Not Implementing Refresh Tokens**: Relying solely on short-lived access tokens without a mechanism to gracefully renew them (via refresh tokens) leads to poor user experience, as users will constantly be logged out. Conversely, using very long-lived access tokens introduces greater security risks.

## Best Practices

*   **Always Use HTTPS**: Ensure all communication involving JWTs occurs over HTTPS to prevent tokens from being intercepted in transit.
*   **Set Short Expiration Times**: Access tokens should have short lifespans (e.g., 5-60 minutes) to minimize the window of opportunity for attackers if a token is compromised.
*   **Implement Refresh Tokens (Securely)**: Use longer-lived refresh tokens (e.g., 7-30 days) to obtain new, short-lived access tokens. Refresh tokens should be stored securely (e.g., in HTTP-only, secure cookies) and ideally be single-use or rotated.
*   **Use Strong, Cryptographically Secure Secrets/Keys**: For symmetric algorithms (like HS256), use long, random, and complex secret keys. For asymmetric algorithms (like RS256), use robust public/private key pairs. Never hardcode secrets in your codebase; use environment variables or a secret management service.
*   **Store Tokens Securely on the Client-Side**:
    *   **Access Tokens**: Prefer HTTP-only, secure cookies to mitigate XSS attacks.
    *   **Refresh Tokens**: Always use HTTP-only, secure cookies. Consider storing these in a dedicated, secure storage for mobile apps.
*   **Validate All Necessary Claims**: On the server-side, always verify the signature, check the `exp` (expiration) and `nbf` (not before) claims, and validate the `iss` (issuer) and `aud` (audience) claims to ensure the token is from the expected source and intended for your application.
*   **Avoid Sensitive Data in Payload**: Remember, the payload is readable. Only include non-sensitive, necessary data (e.g., user ID, roles, permissions).
*   **Consider Token Revocation Mechanisms**: For critical scenarios (e.g., user logout, password change, account deactivation, token compromise), implement a server-side blacklist or a short-term caching mechanism to invalidate active tokens before their natural expiration.
*   **Rate Limiting**: Apply rate limiting to authentication endpoints and refresh token endpoints to prevent brute-force attacks.

## Summary

JSON Web Tokens (JWTs) are a foundational technology for modern, secure, and scalable web and API authentication. They provide a compact, URL-safe, and self-contained way to transmit digitally signed information between parties. A JWT comprises three parts: a Header (metadata), a Payload (claims about the user or entity), and a Signature (for integrity and authenticity verification).

Their primary importance lies in enabling **stateless authentication**, which significantly improves application scalability and simplifies complex architectures like microservices. While offering immense benefits such as ease of use with mobile apps and cross-domain compatibility, it's crucial to understand their limitations, particularly the lack of inherent revocation and the non-encrypted nature of the payload.

Best practices, including using HTTPS, setting short expiration times, securely storing tokens (preferably in HTTP-only cookies), employing strong secrets, and validating all claims, are paramount to mitigating security risks. By understanding the core principles, advantages, disadvantages, and best practices, developers can leverage JWTs effectively to build robust and secure applications.
